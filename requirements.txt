# EXACT pins below (transformers, trl), not ranges -- ranges are what caused this. Two
# separate incidents on two separate fresh installs:
#   1. transformers>=4.46 renamed Trainer.__init__'s `tokenizer=` arg to `processing_class=`
#      with NO backward-compatible kwarg. Our trl (<0.12) unconditionally passes
#      `tokenizer=` into Trainer.__init__ (that's what SFTTrainer(tokenizer=...) does under
#      the hood), so any transformers>=4.46 breaks it with
#      `TypeError: Trainer.__init__() got an unexpected keyword argument 'tokenizer'`.
#   2. Separately, trl's sft_trainer.py unconditionally does
#      `from liger_kernel.transformers import AutoLigerKernelForCausalLM` whenever
#      liger-kernel happens to be importable. liger-kernel>=0.7.0 hard-requires
#      transformers>=4.52.0 (raises its own ImportError otherwise) -- so if a liger-kernel
#      that new is ALREADY present in the runtime (e.g. Colab's base image ships one; it is
#      NOT a dependency of anything in this file), it collides with pin #1 above. This
#      project doesn't use liger-kernel's fused kernels -- trl only imports it
#      opportunistically -- so the fix is to make sure it's ABSENT, not to pin a version:
#      `pip uninstall -y liger-kernel` after `pip install -r requirements.txt` (see
#      README.md's Environment section). We could not verify a liger-kernel version pin
#      against transformers==4.45.2 ourselves -- liger-kernel depends on `triton`, which has
#      no macOS wheels, so it cannot be installed on a CUDA-less dev machine at all, under
#      any version. Excluding it is the only fix we could actually verify end-to-end.
